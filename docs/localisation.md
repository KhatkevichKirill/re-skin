# Localisation project type — design spec / build contract

This file is the **interface contract** every part of the feature is built
against. If an implementation disagrees with this document, the document wins —
raise the conflict rather than silently diverging.

## 0. What this repo ships vs. what the spec describes

The spec below was written against a deployment that also has a **clip library**
and per-run **stitch plans**, so §1 describes the delivered creative as
"localised hook + a language-matched tail from the library". That library is not
part of this repository. Here:

* the hook is transcribed, translated and re-generated exactly as specified;
* the rest of the source stays as one `keep` segment and is delivered as the
  **original, untranslated footage** — trim or replace it downstream if that is
  not what you want to ship.

Everything else in this document — the transcript contract (§4.1), the
`app/localisation.py` API (§4.2), the prompt requirements (§4.3), the endpoints
(§4.4), the hook-window precedence rules, the one-line-one-segment partition, the
segmentation strategy (§5), the `ProjectTypeSpec` fields (§6), the UI (§7) and
the failure behaviour (§8) — is implemented as written. Passages about
`stitch_plan`, `library_clips` and tail selection describe the other deployment
and are kept for reference.

## 1. What the feature does

An operator uploads an ad creative in one language and delivers the same
creative with its **hook** re-spoken in another language. The hook is
regenerated by Seedance; the rest of the source is discarded and a
pre-uploaded language-matched tail from the clip library is stitched on.

Proven manually by run `1736426f` (project `77dc2f0e`, `MarissaHooks_Outdoor_jp`):
`seedance-2-5`, `audio_mode=seedance`, project `mute_source=true`, one 10s swap
segment, `stitch_plan` = that segment only, translated JA dialogue embedded in
the run prompt with speaker labels.

Two modes, chosen per run by the operator:

- **speech only** — the person on screen is preserved, only the spoken
  language changes. No reference image needed.
- **speech + character** — the classic face swap *and* the language change
  (what `1736426f` did). Reference image expected.

## 2. Non-negotiable pipeline settings

These are properties of the type, not operator preferences:

| Setting | Value | Why |
|---|---|---|
| `VideoProject.mute_source` | default **true** | Seedance mixes the original language into its output when it can hear the source track. Muting the upload beats prompting. |
| `Run.audio_mode` | default **`seedance`** | `original` overlays the source (untranslated) soundtrack over the generated video, silently destroying the localisation. |
| Model | must have `produces_audio=True` | Gemini Omni never emits audio, and `create_run` force-downgrades such runs to `audio_mode="original"` — unusable here. |
| Default model | **`seedance-fast`** (Seedance 2.0 Fast) | Operational default: faster and cheaper for routine localisation. Hard ceiling **15s per generated clip** — longer material must be split into valid segments (the project `max_segment_sec` / hook clamp already keep proposed hooks ≤ the segmentation cap; submit-time validation refuses to send an over-limit clip). **Seedance 2.5** remains registered and selectable when its 30s ceiling or explicit `generate_audio` switch is worth the extra cost. |

The proven first run (`1736426f` above) used Seedance 2.5; that is historical
evidence, not the current New Run default.

## 3. Data model

### 3.1 `video_projects` (new columns)

- `project_type` enum is **created** with all four values including
  `localisation` (migration `b1f3d5a7c920`). In a deployment that already had
  the other three types this is instead an `ALTER TYPE ... ADD VALUE
  IF NOT EXISTS`, which is irreversible.
- `hook_sec` FLOAT NULL — how long the localised hook is, as the operator
  intends it. Consumed at **analyze** time (same contract as
  `max_segment_sec`): changing it only affects the next analysis, which is what
  `POST /projects/{pid}/analyze` is for. NULL →
  `settings.LOCALISATION_DEFAULT_HOOK_SEC`. It is the *intent*, not the window
  the transcript is sliced to — analysis clamps the hook and the operator can
  drag the boundary afterwards, and neither writes back here. See §4.4 "The
  hook window: intent vs. reality vs. override".
- `transcript` JSON NULL — the cached transcript (§4.1).
- `transcript_status` VARCHAR(16) NULL — `pending | running | ready | failed | empty`.
  NULL = never requested. `empty` = the model found no speech (a legal
  outcome, not an error).
- `transcript_error` TEXT NULL.

### 3.2 `library_clips` (new column) — NOT IN THIS REPO

- `language` VARCHAR(8) NULL — one of `app/languages.py`'s codes. Drives the
  New Run form's automatic tail selection. NULL = language-agnostic clip.

  There is no clip library here, so this column and the tail auto-selection it
  drives are not part of this branch (see §0).

### 3.3 `runs` — NO new columns

The translated script lives in `Run.prompt` (and `RunSegment.prompt_override`
when the hook spans more than one segment), which is already the record of what
a run did. The target language is the existing `Run.language`. The
speech-only/speech+character choice is a **form-level** toggle that selects a
prompt template — it is not persisted separately, because the prompt and the
reference list it produced already record the outcome.

One migration for all of the above: `b1f3d5a7c920`, which also adds
`video_projects.project_type` / `mute_source` and `runs.language` — on this
branch the whole project-type registry arrives together with localisation.

## 4. Contracts

### 4.1 Transcript JSON

Stored verbatim in `video_projects.transcript`.

```jsonc
{
  "schema_version": 2,
  "model": "gemini-2.5-pro",          // resolved model actually used
  "prompt_version": "transcribe/v2",  // localisation.TRANSCRIBE_PROMPT_VERSION
  "created_at": "2026-08-09T12:00:00Z",
  "source_language": "en",            // ISO 639-1, DETECTED (never assumed)
  "video_summary": "A street interview promo: an off-screen interviewer asks a woman about listening to emails, then she demonstrates the product.",
  "scene_context": "Off-screen interviewer holding the camera; woman in a patterned shirt holds a phone. 'Oh, I'm not.' answers whether she is reading emails the hard way. Product is Speechify.",
  "lines": [
    {
      "id": 1,                        // 1-based, stable, used to re-join translations
      "start": 0.0,                   // seconds from source start
      "end": 2.4,
      "speaker": "off-screen interviewer (camera person)",
      "on_screen": false,             // is the speaker visible in frame
      "text": "Hey, what are you doing?"
    }
  ],
  "on_screen_text": [                 // captions/overlays — NOT translated
    { "start": 0.0, "end": 3.0, "text": "..." }
  ]
}
```

Rules:
- `video_summary` is a short, high-level description of the video's narrative,
  purpose and progression ("what is this about and what happens?"). It must not
  restate the transcript line by line.
- `scene_context` is translation-oriented situational evidence: who is doing
  what, speaker relationships, referenced objects, visible actions, tone,
  jokes, idioms, deictic phrases. Grounded in the video; must not invent facts.
  Keep it distinct from `video_summary`.
- Both are plain strings. New transcriptions always store them (empty string
  when the model omitted a usable value). Cached v1 transcripts that lack
  either field still translate — callers treat a missing key as `""`.
- `speaker` is a **visually grounded, free-text role**, not `speaker_0`. It is
  handed to Seedance, which must be able to map the line onto a person it can
  see ("the woman in the red jacket", "off-screen interviewer"). This is the
  single most important property of the transcript and the reason we use a
  video-capable model rather than ASR diarization.
- `text` is **verbatim** — fillers, false starts and repetitions preserved.
  Line length drives timing; "improving" the text breaks the fit.
- `lines: []` with `transcript_status="empty"` is legal (hook with no speech).

### 4.2 `app/localisation.py` public API

```python

TRANSLATE_PROMPT_VERSION  = "translate/v2"

def transcribe_video(video_path: str, *, kie=None, model: str | None = None) -> dict
    # -> the §4.1 dict. Raises LocalisationError on API/parse failure.

def translate_lines(lines: list[dict], *, source_language: str,
                    target_language: str, model: str | None = None,
                    video_summary: str = "", scene_context: str = "") -> list[dict]
    # -> same lines with "text" replaced by the translation and
    #    "source_text" carrying the original. Same ids, same order, 1:1.
    #    video_summary / scene_context are optional keyword-only inputs
    #    injected into the translate prompt; omit them (or pass "") for
    #    old cached transcripts.

def slice_lines(lines: list[dict], start: float, end: float) -> list[dict]
    # Lines overlapping [start, end). Used to cut the hook window.

def format_dialogue(lines: list[dict]) -> str
    # "**Speaker:**  text" blocks, the shape proven in run 1736426f.

def build_prompt(*, lines, source_language: str, target_language: str,
                 swap_character: bool) -> str
    # Assembles the final Seedance prompt from the template + dialogue.
```

Provider split (they have **different** API shapes — do not build a shared
"universal LLM client", two functions is the honest design):

- **transcribe** → `POST https://api.kie.ai/{model}/v1/chat/completions`
  (OpenAI-compatible, model in the PATH). Video is passed as
  `{"type": "image_url", "image_url": {"url": "<kie upload url>"}}` — kie.ai
  uses that envelope for every media type. Send `stream: false`.
  Get the public URL with the existing `KieClient.upload_file()`.
- **translate** → `POST https://api.kie.ai/codex/v1/responses` (Responses API,
  model in the BODY). Only `input_text` / `input_image` content types exist —
  no `response_format`. `reasoning.effort` defaults to `low`; send `medium`.

Three things verified live against kie.ai (2026-08-09) that the docs get wrong,
and that every caller must respect:

1. **`response_format` json_schema is NOT honoured.** Even with
   `"strict": true`, Gemini returns its object wrapped in a ``` fence. The
   schema is still worth sending (it steadies the field set) but the tolerant
   parse — strip fences, take the outermost `{...}` — is the real contract on
   **both** routes, not just the Responses one.
2. **kie.ai reports errors as HTTP 200** with `{"code":401,"msg":…,"data":null}`
   on both routes. `resp.is_success` proves nothing; sniff the body.
3. **The Responses `output` array has no fixed index for the message.** A live
   `effort=medium` call returned the message at index 0 with no reasoning item,
   contradicting the published example. Scan for `type=="message"` →
   `type=="output_text"` instead of indexing.

The `/codex/v1/responses` route is a Codex proxy and echoes a coding-agent
system persona in `instructions`; the translate prompt therefore ends with an
explicit no-commentary / no-fence instruction.

### 4.3 Prompt design requirements

Constants live in `app/localisation.py`, versioned by the `*_PROMPT_VERSION`
strings above. The final Seedance prompt templates live in
`app/project_types.py` with the other default prompts.

**Transcription prompt** must:
- detect the source language rather than assume it;
- emit a grounded `video_summary` (high-level narrative/purpose) and a distinct
  `scene_context` (situational evidence for translating ambiguous dialogue);
- label speakers by what is visible on screen (§4.1);
- separate spoken dialogue from on-screen text into the two fields;
- stay verbatim;
- emit timestamps per line;
- return zero lines rather than inventing dialogue when there is no speech.

**Translation prompt** must:
- receive each line's **duration in seconds** and target the same *spoken*
  duration, not the same word count (literal EN→JA overruns badly and the hook
  either races or does not fit);
- receive `video_summary` and `scene_context` and use them to resolve meaning
  while preserving the hard 1:1 / timing / brand constraints;
- be free to rephrase — this is ad copy, punch beats literalness;
- leave brand/product names (e.g. Speechify), numbers and prices untranslated;
- keep the original's casual spoken register;
- use the target language's native script, never romanisation;
- return the lines 1:1 with ids preserved;
- never translate `on_screen_text`.

**Seedance prompt templates** (two, both with `{source_language}`,
`{target_language}`, `{dialogue}` slots):
- `_LOCALISATION_SWAP_PROMPT` — replace the on-screen person with the reference
  character **and** re-speak the assigned translated dialogue. Requires natural
  lip sync / mouth timing for the target language, plus speech-related facial
  expressions and reactions. Preserves non-speech continuity (framing, camera,
  background, lighting, props, device screens and their contents, captions /
  on-screen text) and overall body action except speech-related adjustments.
  Does **not** ask the model to freeze original lip motion.
- `_LOCALISATION_KEEP_PROMPT` — same speech / lip / continuity rules, but keep
  the original person's identity, appearance, hair and clothing (no character
  replacement).

Early localisation inherited a face-swap paragraph (historical run `1736426f`)
that said to keep "the original motion and lip movements". That wording
conflicts with localisation and is no longer the contract. Model output is
probabilistic: the prompt instructs adaptive lips and reactions, but perfect
sync is not guaranteed for every clip or language.

### 4.4 HTTP endpoints

```
POST /api/v2/projects/{pid}/transcribe        -> 202, enqueues, status=pending
     -> 409 when the source video is not on disk yet
GET  /api/v2/projects/{pid}/transcript        -> {status, error, transcript}
PATCH /api/v2/projects/{pid}/transcript       -> body: the §4.1 dict; operator fix-ups
POST /api/v2/projects/{pid}/analyze           -> 202 {project_id, status}
     Re-runs analysis. Destructive — see below.
     -> 409 while the project is analyzing
     -> 409 while any run of the project is non-terminal
POST /api/v2/projects/{pid}/localisation-prompt
     Form: language (required, languages.py code), swap_character (bool),
           hook_sec (optional float override, does NOT re-segment)
     -> 200 {source_language, target_language, hook_sec, prompt,
             segment_prompts: {segment_def_id: text}, lines: [...],
             warnings: [str]}
     -> 409 when the transcript is not ready
     -> 422 when the hook window contains no speech
     -> 502 on an upstream model failure
```

Error details are operator-facing strings that the panel renders verbatim in an
alert. Never interpolate a status enum with `!r` (or bare `str()`) — both leak
`<ProjectStatus.ready: 'ready'>`; use the plain `.value`
(`api_v2._status_text`). The remedy the message names must match the state it
reports: "wait for analysis" is only true before analysis has finished.

#### The hook window: intent vs. reality vs. override

Three different numbers can call themselves "the hook length", and conflating
them is what produced a 15-second script for a 10-second clip. In precedence
order, as resolved by `api_v2._resolve_hook_sec`:

1. **The per-call override** — the `hook_sec` form field on
   `localisation-prompt`. Applies to that one call, is never persisted, and
   re-segments nothing: it only changes which lines are translated. It may
   therefore legitimately ask for more dialogue than the analyzed clips can
   say, and warns when it does.
2. **The analyzed reality** — the DEFAULT window. Where the project's swap
   SegmentDefs actually end (capped by the intent), because that is what a run
   will actually generate. Derived on read, never stored.
3. **The stored intent** — `VideoProject.hook_sec`. What the operator asked
   for. It bounds (2), it is what the NEXT analysis cuts to (§3.1), and it is
   the fallback when there are no swap segments to measure. It is never
   rewritten to match reality.

So a project created with `hook_sec=15` under the default 10s segmentation cap
keeps 15 in the column — raise the cap and re-analyze and it finally gets 15 —
while `localisation-prompt` cuts 10s of transcript, because `swap[0,10]` is the
clip that will speak it. The `hook_sec` field in the response is always the
window that was really used, so the UI can display it.

#### One line, one segment

When the hook spans more than one swap segment, each line is assigned to
**exactly one** of them: the segment whose `[start_sec, end_sec)` contains the
line's **midpoint**. `slice_lines` (overlap semantics) is right for cutting the
hook out of the full transcript and wrong for this partition, because a
per-segment `prompt_override` REPLACES the run prompt rather than extending it
(`pipeline_v2`: `prompt_override if prompt_override else run_prompt`). Under
overlap, `swap[0,5] + swap[5,10]` with a line at 4.8–5.4s puts it in both
clips and the stitched hook says the sentence twice; `swap[0,3] + keep[3,5] +
swap[5,10]` with a line inside `[3,5)` puts it in neither and loses it
silently. Both shapes are one drag away in the Segment Editor.

A line straddling a boundary is still assigned whole (a model cannot be handed
half a sentence) and warned about, exactly as at the hook edge. A line stranded
in a gap is warned about **by name** — it is the only trace it leaves.

`warnings` is advisory — the prompt is always returned — and covers the five
things that are invisible in the prompt text and expensive to discover after a
generation is paid for:

1. a line cut mid-sentence, at the hook edge or at a seam between two swap
   segments;
2. a translated line whose spoken length will not fit its shot;
3. a source language equal to the target;
4. a hook window the swap segments do not fully cover, measured as the UNION of
   their coverage inside `[0, hook)` so a hole in the MIDDLE counts — not
   `max(end_sec)`, which read a keep gap as fully covered. Reached by a
   `hook_sec` override asking for more than exists, and by a hand-split hook.
   The degenerate case (no swap segment over the hook at all) gets the blunter
   version: this prompt is text no clip will ever receive;
5. a line stranded in one of those gaps. Suppressed when no per-segment prompts
   were produced at all, since then the run prompt *is* what the single swap
   segment receives and nothing is lost.

`localisation-prompt` writes **nothing** to the database. It returns text the
New Run form drops into its fields; the operator edits it and submits the run
through the existing `create_run` path (`prompt` + `segment_prompts`).

`segment_prompts` is only populated when the hook spans more than one swap
segment; with the usual single-segment hook it is `{}` and the whole dialogue
goes into `prompt`. When it IS populated it covers **every** swap segment of
the hook, including a silent one (whose prompt carries an empty dialogue
block) — a segment left out of the map would fall back to the run prompt, i.e.
to re-speaking the entire hook.

#### `POST /projects/{pid}/analyze`

The only way an analyze-time setting can take effect after creation. Both
`max_segment_sec` and `hook_sec` are consumed when the segments are cut, so the
sequence is `PATCH /projects/{pid}` then this; before it existed the only
remedy was deleting and recreating the project.

Destructive by construction: `analyze_project` deletes every `SegmentDef`
before writing the new proposal, which cascades to every `RunSegment`.

- **Survives**: every `Run` row — prompt, refs, model, status, and for a
  finished run its delivered video and `result_local_path`. A `done` run stays
  done and its video stays playable. So do the source file, transcript, name
  and settings.
- **Does not survive**: every `SegmentDef` (the ids change, so stored
  `stitch_plan` entries and per-segment `prompt_override`s naming one are
  gone) and every `RunSegment` of every run, including finished ones — the
  per-segment breakdown and the "re-run this segment" button go with them. A
  `failed`/`incomplete` run becomes unretryable; retry it first if you want it.

Guards mirror `DELETE /projects/{pid}`, for the same reason (both delete rows a
worker may hold): 409 while the project is `analyzing`, and 409 while any run
is in `queued | processing | stitching | delivering`. `created`, `done`,
`failed` and `incomplete` runs do not block.

On a `localisation` project it also sets `transcript_status="pending"`, because
analysis chains a fresh transcription (§8) — the same reason project creation
writes it. The previous transcript stays readable until the new one lands, but
`localisation-prompt` gates on the status and 409s until then.

## 5. Segmentation

`ProjectTypeSpec` currently encodes strategy as two mutually exclusive booleans
(`detect_faces`, `scene_detect`). Adding a third boolean invites bugs — replace
them with a single field:

```python
SEG_DETECT_FACES = "detect_faces"
SEG_SCENE_DETECT = "scene_detect"
SEG_HOOK_SPLIT   = "hook_split"
SEG_BLANK        = "blank"
segmentation: str
```

Update the three branches in `pipeline_v2.analyze_project` and every reader.

`hook_split`:
```
hook = clamp(project.hook_sec or LOCALISATION_DEFAULT_HOOK_SEC,
             lo = the smallest min_clip_sec in the registry,
             hi = min(effective segmentation cap, duration))
segments = swap[0, hook] (+ split into <= cap chunks if hook > cap)
         + keep[hook, duration]   (omitted when hook >= duration)
```

## 6. New `ProjectTypeSpec` fields

- `segmentation: str` (§5, replaces the two booleans)
- `default_audio_mode: str` — `"original"` everywhere, `"seedance"` for localisation
- `default_mute_source: bool` — False everywhere, True for localisation
- `requires_audio_model: bool` — True for localisation; filters the New Run
  model list by `ai_models.spec_for(m).produces_audio`
- `default_model: str` — localisation defaults to `seedance-fast` (15s per
  clip). Seedance 2.5 stays available as an explicit operator choice for
  longer hooks / `generate_audio`.

## 7. UI

**Create-project form** — `hook_sec` field, shown only when type = localisation.
`mute_source` checkbox pre-checked from `default_mute_source`.

**New Run form** (localisation projects only):
- radio: *Только речь* / *Речь + смена персонажа* — switches the pre-filled
  prompt template; the reference-image input is marked required (client-side)
  in the second mode.
- language `<select>` already exists (`Run.language`); it now also drives the
  translation target and the tail pick.
- **"Перевести"** button → `POST /localisation-prompt` → fills the prompt
  textarea and the `.seg-prompt-field` textareas. Disabled while the transcript
  is not `ready`. Shows returned `warnings` inline.
- model `<option>` list filtered by `requires_audio_model`; `audio_mode`
  pre-set to `seedance` with a warning if switched to `original`.
- stitch plan pre-filled: hook segment included, keep segment excluded, tail
  auto-selected from the library by matching `language`. *(Not in this repo —
  see §0. The hook segment and the keep segment are both stitched, so the
  delivery is the localised hook followed by the original tail.)*

**Project page** — transcript panel: status, detected language, the lines with
timestamps, a "Распознать заново" button, inline editing (PATCH).

## 8. Failure behaviour

- Transcription runs as its **own RQ task after** `analyze_project`, never
  inside it: a Gemini outage must not fail analysis or block segmentation.
- `transcript_status="failed"` leaves the project fully usable — the operator
  pastes a translation by hand, exactly as today.
- `transcript_status="empty"` is surfaced as "no speech in the hook", and the
  Translate button stays disabled.
